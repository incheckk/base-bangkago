[A] PRODUCT RULES TO REVISIT AT LAUNCH
--------------------------------------------------------------------------------
1. STRICT QUEUE-ONLY CAN STALL REQUESTS
   Rule: a booking departing a port can ONLY be accepted by boats currently
   queued (inside the 300m perimeter, 5-min dwell) at that port. If no boat
   is inside the perimeter, the request waits indefinitely.
   HOLD: accepted for now (demo). At launch, decide whether to add a
   fallback (e.g., open the request to all online boats after X minutes,
   or auto-alert the nearest boats).
   Decision date: deferred by user request.

2. DISPATCH HOLD TIMEOUT = 3 MIN, DWELL = 5 MIN, POSITION FRESHNESS = 3 MIN
   Tunable numbers chosen for demo pacing. Revisit with real-world boat
   turnaround data at launch.

3. OFFLINE/STALE BOAT RULES
   Listed-but-offline boats appear on port lists but never receive holds.
   Phone asleep / app killed = boat drops from dispatch after 3 min (no
   GPS fix). Only correct once background tracking ships (item B1).

4. ISLAND-HOP BOOKINGS HAVE NO COMPANION LIST (Phase 4B)
   Package bookings take a PASSENGER COUNT only — no per-companion
   names/IDs, so the sailings manifest for packages shows the head
   count. If coastguard passenger manifests must name every rider,
   add a companion form before launch.

5. BOAT RENTAL HOURLY RATE DEFAULT (Phase 4C)
   bangkas.hourly_rate defaults to ₱500 (migration 016) when a
   operator never set one; rates are editable per boat in
   (bangkero)/rentals. Confirm real per-boat pricing with operators
   before launch.

[B] ROADMAP FEATURES NOT YET BUILT (phases after Phase 2)
--------------------------------------------------------------------------------
B1. BACKGROUND GPS TRACKING
    Currently foreground-only (Expo Go limitation). Needs a dev build /
    production build with expo-location background permission so port
    queues and dispatch work with the screen off.

B2. PUSH NOTIFICATIONS
    Offer/hold-cascade alerts are realtime chips only. Dedicated
    "notifications" phase = push (expo-notifications) for:
    - "You are #1 — offer held for you"
    - hold cascaded to you
    - booking accepted / boarding / no-show / trip updates

B3. (shipped — Phase 3A: bangkero gates, migrations/010_bangkero_gates.sql)
B4. DEPARTURE FLOW POLISH (roadmap item 5)
B5. GPS EN-ROUTE TRACKING FOR PASSENGERS (roadmap item 6)
    Live boat position on the passenger trip screen (trip-en-route.tsx
    placeholder exists).
B6. (shipped — Phase 3B: documents verify flow + GCash QR, migrations
    011_documents_storage.sql / 012_mark_paid.sql)
B7. DISPUTE COUNTER-REPORT — bangkero side deliberately not built.
B8. PASSENGER-HOME BAN BANNER — deliberately not built (ban blocks at
    booking time only).
B9. REAL GCASH PAYMENT INTEGRATION
    Today: booking creates a 'pending' payment (cash and GCash alike);
    the bangkero marks it paid ON BOARD (mark_paid RPC, migration 012)
    with an OPTIONAL manual reference number. There is NO scan-to-pay
    step yet — a passenger camera reading the bangkero's GCash QR and
    auto-confirming payment is deliberately deferred. Wire a real
    GCash/API gateway (and the scan flow) at launch.
    Escrow (Phases 4B/4C): island-hop packages and boat rentals file
    their 50% downpayment against the ADMIN's GCash QR (app_settings
    row 'gcash_qr_url', Admin → GCash QR) as a reference number +
    screenshot upload into the downpayments table (migration 015).
    Everything is settled OUT OF BAND: approve/refund is a manual
    Admin → Downpayments button, nothing moves automatically. Rental
    remainders are collected CASH IN PERSON when the charter
    completes; package remainders are a 'cash' payment row collected
    onboard. No real gateway in any of these paths yet.
B10. DEMAND PREDICTION (ML)
    DemandBadge on bangkero home shows placeholder numbers. Per the
    knowledge base: Phase 1 = collect >1000 bookings; Phase 2 = train
    model + deploy FastAPI; Phase 3 = integrate predictions; Phase 4 =
    admin fleet optimization.
B11. NATIVE MAPS (dev build): react-native-maps + OSM tiles instead of
    WebView-based map (KB "Future" item).
B12. COASTGUARD / LGU — FOURTH MOBILE ROLE (view-only)
     Papers/design treat the system as FOUR mobile roles: Admin,
     Bangkero, Passenger, and Coastguard/LGU — a view-only tier with
     lower permissions than admin. Current build has only the first
     three (UserRole in types/models.ts). Intended scope: read-only
     screens only — View Live Port Queues and View Routes & Fares
     (reuse admin views); NO route/port editing. To build later:
     extend UserRole, sign-in role routing, menu.ts, and the
     role-guard redirects in the _layout files.
