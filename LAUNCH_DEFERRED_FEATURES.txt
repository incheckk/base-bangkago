[A] PRODUCT RULES TO REVISIT AT LAUNCH
--------------------------------------------------------------------------------
1. STRICT QUEUE-ONLY CAN STALL REQUESTS
   Rule: a booking departing a port can ONLY be accepted by boats currently
   queued (inside the 300m perimeter, 5-min dwell) at that port. If no boat
   is inside the perimeter, the request waits indefinitely.
   HOLD: accepted for now (demo). At launch, decide whether to add a
   fallback (e.g., open the request to all online boats after X minutes,
   or auto-alert the nearest boats).
   Decision date: deferred by user request.

2. DISPATCH HOLD TIMEOUT = 3 MIN, DWELL = 5 MIN, POSITION FRESHNESS = 3 MIN
   Tunable numbers chosen for demo pacing. Revisit with real-world boat
   turnaround data at launch.

3. OFFLINE/STALE BOAT RULES
   Listed-but-offline boats appear on port lists but never receive holds.
   Phone asleep / app killed = boat drops from dispatch after 3 min (no
   GPS fix). Only correct once background tracking ships (item B1).
   2026-11-17: the bangkero app now re-reports its last fix every 45 s
   while the tracker is running in the foreground, so a docked boat no
   longer ages out of dispatch on a stationary phone (iOS fires the
   watcher on distance, not time). Background/asleep still drops - JS
   timers do not run there.

4. ISLAND-HOP / RENTAL COMPANION LIST (Phase 4B/4C)
   SHIPPED in the M1-M6 build: book-package and rental-form capture
   companions through the shared CompanionForm; rows land in
   passenger_details (booking_id for rides, boat_rental_id for rentals,
   migration 026) and render for passenger AND bangkero. The edit pencil
   (2026-10) opens prefilled with Save changes / Remove passenger. Migration
   083 (2026-11-16) makes this work AFTER the booking exists: owner,
   assigned operator, and Admin can update details, while removal is the
   atomic remove_passenger_detail() RPC so pax count and fare move together.
   Edits lock after boarding/departure; removal also refuses filed
   downpayments and completed/refunded fares. Raw DELETE stays unavailable.

5. BOAT RENTAL PRICE TIER DEFAULT (Phase 4C, updated 2026-10-22)
   A boat with no saved bangkas.standard_price (migration 068) quotes
   the demo capacity tier: under 15 pax ₱3,500, 15+ ₱7,000. Prices are
   editable per boat in (bangkero)/rentals and web Manage Bangka.
   Confirm real per-boat whole-day pricing with operators before launch.

6. AUDIT TRAIL DOES NOT ATTRIBUTE SQL-EDITOR WRITES (migration 082)
   Migration 082 records authenticated app/web business changes with
   semantic activity names, actor and record snapshots, and safe
   before/after values. Generated notifications and GPS/weather telemetry
   are excluded; notification read-state changes are included. Writes made
   directly in the Supabase SQL editor or with the service-role key have
   no user JWT and are not attributable. Route administrative changes
   through authenticated app/web actions if they must be audited. Existing
   038 entries are relabelled from their stored changes, but cannot recover
   intent that was never captured. Audit access remains admin-only.

7. FLEET MAP ETA/DIRECTION TEXT IS AN ESTIMATE (web batch 2026-10-16)
   The Leaflet/OSM fleet maps (fleet-map.js on admin + coastguard
   monitor-fleet and coastguard index) plot REAL vessel_tracking fixes,
   but the "ETA"/delay text on the route pills is derived from fix age
   only (Stable <60s, Intermittent <5min, Lost after) — there is no
   heading/speed→arrival math. Same class as the mock ETA in
   monitor-fleet's vessel panel. Wire real routing/ETA only if a demo
   script needs it.

8. BATCHED PARCEL RESOLUTION IS CLIENT-TRIGGERED (Parcel Padala 054)
   A batched parcel's shared crossing booking is created by
   resolve_batch_rpc when the batch window closes. Today the trigger is
   a client-side deadline check in (passenger)/batched-waiting.tsx
   (fired from load(): mount, 15s poll, realtime/focus). If every
   sender closes the app before the 1-hour deadline - Expo Go pauses
   JS while backgrounded - the batch never resolves: parcels stay
   pending_batch, the sailing manifest misses them, and completion only
   auto-delivers the parcel whose stub was linked. The RPC is
   idempotent, so a late call is safe - the batch is delayed, not lost.
   Production fix: a server-side scheduled job (pg_cron) that calls
   resolve_batch_rpc for every route key with an expired deadline.

9. LIVE SEA WEATHER COMES FROM OPEN-METEO, NOT THE weather_data TABLE (2026-10-21)
   Every weather surface (passenger home, bangkero home, admin home,
   coastguard home, admin + coastguard web dashboards) now reads
   Open-Meteo directly: free for NON-COMMERCIAL use, no API key, no
   billing — the CC BY 4.0 "Weather data by Open-Meteo" credit line is
   mandatory and must not be removed. Points are fixed demo coordinates
   (Mactan 10.3022/124.0184, Cebu Strait 10.26/124.0), not the boat's
   live position. The marine endpoint refuses land points, so wave
   height is nullable and the card prints "waves n/a" rather than
   failing. Cached 15 min (AsyncStorage / localStorage) with a stale
   fallback, and the refresh only runs while the app is foregrounded.
   Before monetising the app, re-check Open-Meteo's commercial terms or
   move behind a server-side proxy. The Supabase weather_data table and
   its service functions (getLatestWeather / getWeatherHistory) are
   untouched but no longer feed any dashboard — the coastguard web page
   and (bangkero)/weather.tsx still read them, so keep the table.

10. IN-APP ACCEPT PING IS FOREGROUND-ONLY (2026-10-21)
    Sound + vibration on accept (bangkero: new request; passenger:
    booking accepted or a notification inserted) run through
    expo-haptics + expo-audio on a realtime subscription. Realtime
    events are not delivered while Expo Go is backgrounded, and local
    notifications remain a no-op on Android in Expo Go — so a phone in
    a pocket stays silent. Same root cause as B1/B2; fixed by a dev
    build with push + background tasks.

11. RETURNED CARGO PARCEL HAS NO FARE ADJUSTMENT (2026-11-09)
    Migration 073 lets the bangkero mark individual parcels "not at
    port" from Booking Status. The parcel becomes returned, and the
    last live parcel cancels the non-accompanied cargo booking, but
    bookings.total_price is NOT re-priced and no refund is issued.
    Decide the money rule before launch: per-parcel refund, re-price
    the booking before departure, or keep the no-show fare.

12. ONE SERVICE MODULE PER BOAT PER SAILING DAY (2026-11-13)
    Migration 079 adds module_lock_ok + trg_bookings_module_lock: once a
    boat accepts a ride it cannot take an island hop that day (or the
    reverse), and a live charter holds the whole day. Same module +
    same route keeps accepting until capacity is full (that is the
    point). The lock is ALWAYS on - no developer switch - while the
    route lock has its own switch (dev_flags.route_lock_bypass) and is
    no longer lifted by the FCFS bypass. Confirm with operators that a
    boat really should never mix a ride and an island hop in one day;
    real operations may want a per-slot version (morning ride,
    afternoon hop) instead of the whole day.

13. ESCROW PAYOUT IS A MANUAL ADMIN LEDGER ENTRY (2026-11-13)
    migration 079 adds released_at / released_to / payout_method /
    payout_ref to downpayments and release_downpayment, which pays the
    held 50% to the operator's own GCash QR (or records cash).
    Nothing moves money: the admin sends GCash by hand and types the
    reference. Since 097 the release deducts the same commission the
    gateway rail deducts (app_settings.commission_rate, a share of the
    WHOLE fare), so the admin sends the net and Earnings' GROSS /
    RELEASED copy stays true. A released row cannot be refunded. Real
    payout rails belong with B9.

14. ISLAND-HOP PRICE IS PER PERSON AGAIN (2026-11-16)
    Migration 068 had re-read island_packages.price as a WHOLE-BOAT
    price; the defense build reverses that (the panel asked for per
    passenger): book-package charges price x pax and every label reads
    "per person". No rows were reseeded - the numbers already in the
    table now mean per person. Web admin edits still write the same
    column, so keep the Manage Bangka / island-package labels in sync.
    Decide the final commercial rule (seat price vs charter price)
    before publishing fares.

15. ONE BOAT PER BANGKERO IS NOW ENFORCED (2026-11-16)
    Migration 081 retires every extra boat (049 soft delete, keeping the
    one with the most history) and adds a partial UNIQUE index per
    bangkero. A real operator may own a fleet; lifting that needs the
    app's single-boat reads (profile, departure, getMyBangkaCapacity) to
    become a boat picker first, and the index to be dropped.

16. DEMO PORTS LIVE IN THE PRODUCTION TABLES (2026-11-16)
    Migration 086 inserts two presentation-only ports (demo-stb "ST
    Building", demo-home "Home") and their two directed routes, all
    INACTIVE. Admin -> Developer Options flips ports.is_active /
    routes.is_active for id LIKE 'demo-%'. They are normal rows, so a
    passenger could book one if an admin ever leaves the switch on.
    Delete the id LIKE 'demo-%' rows before public launch (and remove
    the Developer Options switch with them).

17. COMPANION NO-SHOW LANDS ON THE BOOKER'S BAN (2026-11-16)
    Migration 088 stamps bookings.no_show_at when a companion is marked
    not_boarded while the booker already sailed, so the BOOKER carries
    the 30/60-minute booking ban and notification even though they rode.
    That was the product decision (the booking is the accountable unit)
    but it is worth revisiting if a booker complains about a companion
    who missed the boat on their own.

18. DEPARTURE LOCK IS UI + RPC, NOT A TABLE TRIGGER (2026-11-16)
    085 refuses boarding/QR writes once depart_time is stamped, and
    088 refuses companion boarding after departure. The screens also
    close themselves (Departure / Booking Status go read-only, en-route
    absorbs back). The raw bookings UPDATE policy (E1) is still broad:
    a crafted client could stamp onboarded_at or un-cancel a sailed
    trip. That narrowing belongs with E1.

19. SAME-DAY RENTALS ARE A DEMO SWITCH (2026-11-16)
    Migration 089 adds dev_flags.rental_today + demo_rental_today_enabled()
    + admin-only set_rental_today(). OFF is the production rule (the
    rental strip starts tomorrow). ON offers Today so a charter can be
    booked for the presentation day; the 50% downpayment, admin escrow
    approval and the 027/079 day locks are unchanged. Decide the
    commercial rule for same-day charters before launch, or delete the
    switch and the flag with it.

20. ISLAND HOP IS OPEN TO ALL BANGKEROS (2026-11-17)
    Migration 098 drops the 084 rule that bound each package to one
    Bangka. island_packages.max_capacity becomes nullable and the app no
    longer reads it; a package needs only a name, itinerary, duration
    and per-person price, and dispatch offers the booking to every
    eligible bangkero (boat capacity rules at accept through 081's
    fits_booking, and 079's one-service-per-boat-day lock still holds).
    Admin web Manage Island Hopping lost the Bangkero/Bangka assign and
    passenger-limit fields, and the Customer Bookings list shows the
    boat only after a bangkero accepts. If real operations ever need a
    dedicated boat per package, that is a new assignment model, not the
    084 guard.

21. A REJECTED RECEIPT DOES NOT CANCEL THE BOOKING (2026-11-17)
    Migration 097 adds downpayments.status 'rejected' + reject_reason
    and reject_downpayment(), and both consoles now offer "Reject
    receipt" beside Approve. Rejecting stores the admin's reason,
    notifies the passenger and leaves the booking pending so the
    passenger can file a new receipt (newest row wins). "Refund" stays
    for money that actually arrived and must go back; it is the action
    that cancels the booking through review_advance_escrow. Rental
    "Send a new receipt" reuses the same boat_rentals row via the
    rental-payment rentalId param, so no duplicate request is created.

22. PASSENGER "I'M NOT ON BOARD" WAS REMOVED BY REQUEST (2026-11-17)
    The 088/2026-11-16 honesty feature (dispute_boarding: trip still
    completes, bangkero notified, Coast Guard safety_alerts row, no
    ban) no longer has a passenger-facing button — removed at the user's
    explicit request for this defense build. The DB RPC, the
    bangkero-side disputedAt handling and the Coast Guard alert reading
    all remain, so re-surfacing it later is a screen change, not a
    migration. Decide whether to restore it before public launch.

B15. PAYMENT GATEWAY — SANDBOX ONLY (095 + 096, 2026-11-17)
     The money loop now runs itself in code: hosted checkout → signed
     webhook confirms the downpayment (confirm_gateway_downpayment, which
     re-runs 020's two effects: booking pending → open + assign_next_hold,
     rental awaiting_payment → pending) → trip completion queues a payout
     (trigger) → gateway payout → record_gateway_payout stamps
     released_at / payout_ref. No admin click in the happy path.
     TODAY THE PROVIDER IS OUR OWN EDGE FUNCTION
     (supabase/functions/gateway, action-routed: create-checkout,
     webhook, payout, plus its signed sandbox page), which moves ZERO
     pesos and says SANDBOX on the page. PayMongo sign-ups are paused, so
     the live branch (GATEWAY_MODE=live + GATEWAY_BASE_URL + GATEWAY_KEY)
     is UNTESTED against a real account — verify with sandbox keys before
     switching. The function must be deployed with "Enforce JWT
     verification" OFF (the sandbox page and webhook are unauthenticated;
     each action authenticates itself with auth.getUser() or the HMAC).
     dev_flags.manual_payments ships TRUE, so the receipt-upload + admin
     release flow above stays the default; Admin → Developer Options
     flips it OFF for the gateway demo and back ON if the API breaks.
     Since 097 that manual rail is honest about failure: a bad receipt is
     REJECTED (reason stored + passenger notified, booking stays payable
     and can be paid again), not "refunded", and the release box shows
     the exact net (held amount − commission) before the admin sends it.
     Money still lives in our ledger: copy says "held by BangkaGo", never
     "held by the provider". Payouts batch — every completed, unpaid
     downpayment a bangkero is owed goes out as ONE transfer with one
     provider ref, and a failed batch marks every row failed (retry from
     Admin → Downpayments).
     Fee: none. Commission is app_settings.commission_rate (default 7%,
     Admin → Downpayments, and editable from Admin web → View Reports →
     Commission since 2026-11-26 — one stored value, both consoles),
     a share of the WHOLE FARE deducted from the
     downpayment, snapshotted onto each row when the payout is claimed so
     a later rate change never rewrites history. Admins see it; the
     bangkero app shows GROSS / RELEASED only. The web Commission report
     covers completed BOOKINGS only — a charter's downpayment carries the
     same commission rule but is settled under Boat Rentals / Downpayments
     and is not in that split yet. That report charges the share on EVERY
     completed fare (the rule above) and separates where it is: withheld
     (released), in escrow (approved, deducted at release), or NOT
     WITHHELD — a same-day fare has no downpayment to take it from, so
     nothing in the app collects that share yet; it would be settled with
     the operator outside the payout.
     Payout account: 095 adds bangkeros.payout_account_name / _number /
     _channel (gcash only). A bangkero without one can still sail — no
     gate — but there is nowhere for the money to land, so the app
     prompts for it on Home, Earnings and Payout & GCash QR.

    Most RPCs from 002-010 are SECURITY DEFINER SET search_path =
    public (should be search_path = '') and rely on Postgres' default
    EXECUTE grant to PUBLIC — i.e. callable by anon over PostgREST
    unless an auth.uid() guard stops them. assign_next_hold had NEITHER
    and was patched in 019 (guard + REVOKE FROM PUBLIC/anon). Remaining
    suspects to audit the same way: append_rejected_by (called out by
    the audit as missing a guard), and every 002-007-era function.
    mark_paid (012), refresh_holds/accept_booking_hold (008/010) already
