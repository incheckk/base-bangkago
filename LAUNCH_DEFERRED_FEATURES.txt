[A] PRODUCT RULES TO REVISIT AT LAUNCH
--------------------------------------------------------------------------------
1. STRICT QUEUE-ONLY CAN STALL REQUESTS
   Rule: a booking departing a port can ONLY be accepted by boats currently
   queued (inside the 300m perimeter, 5-min dwell) at that port. If no boat
   is inside the perimeter, the request waits indefinitely.
   HOLD: accepted for now (demo). At launch, decide whether to add a
   fallback (e.g., open the request to all online boats after X minutes,
   or auto-alert the nearest boats).
   Decision date: deferred by user request.

2. DISPATCH HOLD TIMEOUT = 3 MIN, DWELL = 5 MIN, POSITION FRESHNESS = 3 MIN
   Tunable numbers chosen for demo pacing. Revisit with real-world boat
   turnaround data at launch.

3. OFFLINE/STALE BOAT RULES
   Listed-but-offline boats appear on port lists but never receive holds.
   Phone asleep / app killed = boat drops from dispatch after 3 min (no
   GPS fix). Only correct once background tracking ships (item B1).

4. ISLAND-HOP / RENTAL COMPANION LIST (Phase 4B/4C)
   SHIPPED in the M1-M6 build: book-package and rental-form capture
   companions through the shared CompanionForm; rows land in
   passenger_details (booking_id for rides, boat_rental_id for rentals,
   migration 026) and render for passenger AND bangkero. Row ✕ was
   replaced by an edit pencil (2026-10): the modal opens prefilled
   with Save changes / Remove passenger. Still open: that edit works
   on the LOCAL list before filing — companions remain INSERT-only in
   the DB (E7), so they cannot be corrected AFTER the booking exists.

5. BOAT RENTAL PRICE TIER DEFAULT (Phase 4C, updated 2026-10-22)
   A boat with no saved bangkas.standard_price (migration 068) quotes
   the demo capacity tier: under 15 pax ₱3,500, 15+ ₱7,000. Prices are
   editable per boat in (bangkero)/rentals and web Manage Bangka.
   Confirm real per-boat whole-day pricing with operators before launch.

6. ADMIN AUDIT TRAIL SKIPS SQL-EDITOR WRITES (web batch 2026-10-16)
   audit_log (migration 038) is trigger-based, so it only sees writes
   with a JWT. Anything an admin types directly into the Supabase SQL
   editor (e.g. hand-editing a fare, forcing a status) is NOT audited.
   Acceptable for the demo; at launch either route those edits through
   the dashboard/RPCs or add a session variable convention the trigger
   reads. Also: the trigger snapshots actor id + role, so a user whose
   role changed later keeps the role they had AT THE TIME (by design).

7. FLEET MAP ETA/DIRECTION TEXT IS AN ESTIMATE (web batch 2026-10-16)
   The Leaflet/OSM fleet maps (fleet-map.js on admin + coastguard
   monitor-fleet and coastguard index) plot REAL vessel_tracking fixes,
   but the "ETA"/delay text on the route pills is derived from fix age
   only (Stable <60s, Intermittent <5min, Lost after) — there is no
   heading/speed→arrival math. Same class as the mock ETA in
   monitor-fleet's vessel panel. Wire real routing/ETA only if a demo
   script needs it.

8. BATCHED PARCEL RESOLUTION IS CLIENT-TRIGGERED (Parcel Padala 054)
   A batched parcel's shared crossing booking is created by
   resolve_batch_rpc when the batch window closes. Today the trigger is
   a client-side deadline check in (passenger)/batched-waiting.tsx
   (fired from load(): mount, 15s poll, realtime/focus). If every
   sender closes the app before the 1-hour deadline - Expo Go pauses
   JS while backgrounded - the batch never resolves: parcels stay
   pending_batch, the sailing manifest misses them, and completion only
   auto-delivers the parcel whose stub was linked. The RPC is
   idempotent, so a late call is safe - the batch is delayed, not lost.
   Production fix: a server-side scheduled job (pg_cron) that calls
   resolve_batch_rpc for every route key with an expired deadline.

9. LIVE SEA WEATHER COMES FROM OPEN-METEO, NOT THE weather_data TABLE (2026-10-21)
   Every weather surface (passenger home, bangkero home, admin home,
   coastguard home, admin + coastguard web dashboards) now reads
   Open-Meteo directly: free for NON-COMMERCIAL use, no API key, no
   billing — the CC BY 4.0 "Weather data by Open-Meteo" credit line is
   mandatory and must not be removed. Points are fixed demo coordinates
   (Mactan 10.3022/124.0184, Cebu Strait 10.26/124.0), not the boat's
   live position. The marine endpoint refuses land points, so wave
   height is nullable and the card prints "waves n/a" rather than
   failing. Cached 15 min (AsyncStorage / localStorage) with a stale
   fallback, and the refresh only runs while the app is foregrounded.
   Before monetising the app, re-check Open-Meteo's commercial terms or
   move behind a server-side proxy. The Supabase weather_data table and
   its service functions (getLatestWeather / getWeatherHistory) are
   untouched but no longer feed any dashboard — the coastguard web page
   and (bangkero)/weather.tsx still read them, so keep the table.

10. IN-APP ACCEPT PING IS FOREGROUND-ONLY (2026-10-21)
    Sound + vibration on accept (bangkero: new request; passenger:
    booking accepted or a notification inserted) run through
    expo-haptics + expo-audio on a realtime subscription. Realtime
    events are not delivered while Expo Go is backgrounded, and local
    notifications remain a no-op on Android in Expo Go — so a phone in
    a pocket stays silent. Same root cause as B1/B2; fixed by a dev
    build with push + background tasks.

[E] P2 SECURITY DEBT — deferred out of the post-4C fix pass
--------------------------------------------------------------------------------
The fix pass took P0 (login recursion, 018) + P1 (manifest/payment/seed
chain) + P3 (polish). The items below were audited, verified, and are
DELIBERATELY NOT FIXED yet. Fix all of this before public launch.

E1. bookings UPDATE STATE-MACHINE BYPASS
    004 constrains the bangkero's transitions (open→accepted,
    accepted→completed), but the passenger-side bookings_update_own
    policy (002) is column-unrestricted: a passenger can UPDATE their
    own booking row — including trip_stat, operator_id, held_by,
    total_price — directly from the client. Move every state transition
    into guarded SECURITY DEFINER RPCs (the accept/complete/no-show
    paths already exist) and revoke broad UPDATE, or add a trigger that
    validates transitions.
    Narrowing 2026-10-20 (056): cancel_own_booking now RAISEs once
    depart_time is stamped, so the RPC path can no longer cancel a
    boat that has sailed. That is ONE path — the broad client UPDATE
    policy itself is untouched and still open here.

E2. CLIENT-WRITABLE WALLET
    wallets / wallet top-ups are written from the client (RLS allows
    the owner to insert their own wallet_transactions with arbitrary
    amounts). Balance mutations must become SECURITY DEFINER RPCs with
    server-side validation before real money exists.

E3. USING (TRUE) PII SELECT POLICIES
    trip_manifest, manifest_passengers and manifest_parcels ship with
    *_select_all policies created WITHOUT a USING clause (defaults to
    true): every authenticated user can read every sailing's passenger
    names, boarding times and parcel recipients. Tighten to
    owner-bangkero / admin before launch; re-audit ALL SELECT policies
    for the same shape (ports/routes/weather are public by design, PII
    tables are not).

E4. SECURITY DEFINER PATTERN + ANON-EXECUTABLE FUNCTIONS
    Most RPCs from 002-010 are SECURITY DEFINER SET search_path =
    public (should be search_path = '') and rely on Postgres' default
    EXECUTE grant to PUBLIC — i.e. callable by anon over PostgREST
    unless an auth.uid() guard stops them. assign_next_hold had NEITHER
    and was patched in 019 (guard + REVOKE FROM PUBLIC/anon). Remaining
    suspects to audit the same way: append_rejected_by (called out by
    the audit as missing a guard), and every 002-007-era function.
    mark_paid (012), refresh_holds/accept_booking_hold (008/010) already
    carry guards — keep them as the pattern.

E5. MIGRATION 017 IS A BLANKET UPDATE
    017_flat_fare_70.sql runs `UPDATE routes SET base_fare = 70` with
    no condition. Re-running it (or running it after an admin edits
    fares) silently resets EVERY route's fare. Fares are admin data
    (manage-routes), not migration constants — make the seed
    idempotent-by-default instead of unconditional before automating
    migrations (D2).

E6. SIGN-UP ORPHANS (email-confirm + profile failures)
    signUp creates the auth user FIRST; if the subsequent users insert
    fails, the auth account remains with no users row — retry answers
    "already registered" and sign-in lands on a profile-less session.
    The bangkeros-insert variant is now handled in code (downgrade to
    passenger, see auth.service.ts), but the users-insert and
    email-confirmation paths are not. Before launch: verify Supabase
    email-confirmation settings, and clean up / roll back orphaned auth
    users on partial failure.

E7. passenger_details HAS NO DELETE (or UPDATE) POLICY
    Companion rows are INSERT-only from the passenger's side — a
    booking's OR rental's companion list can never be corrected or
    removed (026 added boat_rental_id, same gap). Add
    passenger-owned UPDATE/DELETE (or an RPC) before launch.

E8. RESOLVED BY 062 — see C3. The one-active-booking-per-passenger
    index is gone by design; 062's trigger enforces the real rule
    (one active same-day booking; advances only clash on the same date
    and slot) with SECURITY DEFINER + REVOKE/GRANT.
